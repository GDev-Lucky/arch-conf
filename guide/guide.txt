== 00. PHILOSOPHY ==
===============================================================================

The point of this machine is not merely "use fewer packages".

The real goals are:

    1. Know what every MAJOR component does.
    2. Let pacman handle boring low-level library dependencies.
    3. Install major tools deliberately.
    4. Write the installation step before or while installing the tool.
    5. Keep configuration in Git.
    6. Test one subsystem at a time.
    7. Do not hide complexity behind a desktop environment.
    8. Do not optimize things you do not yet understand.

A dependency such as a shared library does not need its own installation ritual.

A major tool does.

Examples:

    libffi
        Let pacman handle it.

    Git
        Learn it deliberately.

    wlroots
        Learn what role it plays.

    PipeWire
        Learn what it replaces and what it does.

    systemd-networkd
        Learn how your network gets configured.

    dwl
        Build it yourself and understand its build system.

A good final state is:

    Every explicit package:
        "I know why I requested this."

    Every enabled service:
        "I know why this runs."

    Every major background process:
        "I can identify who started it."

== 02. FIX THESE FIRST-BOOT ISSUES BEFORE ADDING ANYTHING ==
===============================================================================

The first health report was good, but two configuration issues should be fixed

-------------------------------------------------------------------------------
02.1 FIX /etc/resolv.conf -> systemd-resolved
-------------------------------------------------------------------------------

WHAT WAS OBSERVED:

    systemd-resolved was active,
    DNS worked,
    but resolvectl reported:

        resolv.conf mode: foreign

WHAT THAT MEANS:

    systemd-resolved is running, but /etc/resolv.conf is not using its normal
    stub resolver symlink.

We want:

    applications
        -> /etc/resolv.conf
        -> 127.0.0.53 systemd-resolved stub
        -> DNS server learned from networkd/DHCP

Inspect first:

    ls -l /etc/resolv.conf
    resolvectl status

Become root:

    su -

Replace /etc/resolv.conf with the resolved stub symlink:

    ln -sf ../run/systemd/resolve/stub-resolv.conf /etc/resolv.conf

Leave root:

    exit

Verify:

    ls -l /etc/resolv.conf
    resolvectl status

You want the mode to report:

    resolv.conf mode: stub

Test name resolution:

    getent hosts archlinux.org

Test connectivity:

    ping -c 3 archlinux.org

WHY `getent`?

    `ping archlinux.org` combines:
        DNS resolution
        + ICMP connectivity

    `getent hosts archlinux.org` isolates the name-service lookup part.

-------------------------------------------------------------------------------
02.2 LOCK DOWN THE FAT /boot MOUNT
-------------------------------------------------------------------------------

WHAT WAS OBSERVED:

    systemd-boot warned that:

        /boot was world accessible
        /boot/loader/random-seed was world accessible

WHY THIS HAPPENS:

    FAT does not store normal Unix permission bits.

Linux therefore synthesizes permissions from mount options such as:

    fmask=
    dmask=
    umask=

Your boot partition was mounted too openly.

Inspect:

    grep -n '[[:space:]]/boot[[:space:]]' /etc/fstab
    findmnt /boot

Backup before editing:

    su -
    cp /etc/fstab /etc/fstab.before-boot-permissions

If the /boot line contains:

    fmask=0022,dmask=0022

replace those with:

    umask=0077

Command:

    sed -i \
        '/[[:space:]]\/boot[[:space:]]/ s/fmask=0022,dmask=0022/umask=0077/' \
        /etc/fstab

Inspect BEFORE remounting:

    grep -n '[[:space:]]/boot[[:space:]]' /etc/fstab

Then:

    mount -o remount /boot

Leave root:

    exit

Verify:

    findmnt -no OPTIONS /boot
    stat -c '%a %n' /boot /boot/loader/random-seed

The exact displayed mode can vary because FAT permissions are synthesized, but
the important thing is that ordinary users are no longer given broad access.

02.5 FIRST CHECKPOINT: BOOT HEALTH ONLY
-------------------------------------------------------------------------------

This health script intentionally checks ONLY the boot/core system.

It does not care whether:
    networking works
    Git works
    NVIDIA works
    dwl exists
    audio exists

Create your project directories first:

    mkdir -p ~/src/launch/{install,health,config,bin,notes,guide}

Create:

    cat > ~/src/launch/health/00-boot.sh <<'EOF'
    #!/usr/bin/env bash
    set -u

    failures=0
    warnings=0

    pass() { printf '[PASS] %s\n' "$*"; }
    warn() { printf '[WARN] %s\n' "$*"; warnings=$((warnings + 1)); }
    fail() { printf '[FAIL] %s\n' "$*"; failures=$((failures + 1)); }

    echo '=== BOOT / CORE HEALTH ==='

    if [[ "$(cat /proc/1/comm 2>/dev/null)" == "systemd" ]]; then
        pass "systemd is PID 1"
    else
        fail "PID 1 is not systemd"
    fi

    if findmnt -rn / >/dev/null 2>&1; then
        pass "root filesystem is mounted"
        findmnt /
    else
        fail "root filesystem could not be inspected"
    fi

    if findmnt -rn /boot >/dev/null 2>&1; then
        pass "/boot is mounted"
        findmnt /boot
    else
        warn "/boot is not currently mounted"
    fi

    if [[ -r /proc/version ]]; then
        pass "kernel is running"
        uname -a
    else
        fail "kernel information unavailable"
    fi

    failed_units="$(systemctl --failed --no-legend --plain 2>/dev/null | sed '/^[[:space:]]*$/d')"
    if [[ -z "$failed_units" ]]; then
        pass "no failed system units"
    else
        fail "failed system units exist"
        printf '%s\n' "$failed_units"
    fi

    if bootctl is-installed >/dev/null 2>&1; then
        pass "systemd-boot is installed"
    else
        warn "bootctl does not report systemd-boot as installed"
    fi

    echo
    printf 'RESULT: %d failure(s), %d warning(s)\n' "$failures" "$warnings"

    (( failures == 0 ))
    EOF

Make executable:

    chmod +x ~/src/launch/health/00-boot.sh

Run:

    ~/src/launch/health/00-boot.sh

This is your CHECKPOINT 0.

Do not proceed if it reports a real FAIL you do not understand.

== 06. PACKAGE-INSTALLATION HABIT ==
===============================================================================

Before a meaningful install:

1. SEARCH:

    pacman -Ss PACKAGE

2. READ PACKAGE METADATA:

    pacman -Si PACKAGE

3. PREVIEW THE TRANSACTION:

    pacman -Sp --needed --print-format '%n  %v  %s  %d' PACKAGE

Fields:

    %n      package name
    %v      version
    %s      download size
    %d      description

4. INSTALL:

    su -
    pacman -Syu --needed PACKAGE
    exit

Why `-Syu`?

    -S      sync/install
    -y      refresh package databases
    -u      upgrade the whole system

Arch is a rolling release.

Avoid partial upgrades such as:

    pacman -Sy PACKAGE

Prefer a full synchronized transaction.

== 07. NETWORK CHECKPOINT ==
===============================================================================

Create:

    cat > ~/src/launch/health/10-network.sh <<'EOF'
    #!/usr/bin/env bash
    set -u

    failures=0
    warnings=0
    pass() { printf '[PASS] %s\n' "$*"; }
    warn() { printf '[WARN] %s\n' "$*"; warnings=$((warnings + 1)); }
    fail() { printf '[FAIL] %s\n' "$*"; failures=$((failures + 1)); }

    echo '=== NETWORK HEALTH ==='

    if systemctl is-active --quiet systemd-networkd.service; then
        pass "systemd-networkd is active"
    else
        fail "systemd-networkd is not active"
    fi

    if systemctl is-active --quiet systemd-resolved.service; then
        pass "systemd-resolved is active"
    else
        fail "systemd-resolved is not active"
    fi

    if [[ -L /etc/resolv.conf ]]; then
        target="$(readlink /etc/resolv.conf)"
        printf 'resolv.conf -> %s\n' "$target"
        if [[ "$target" == *systemd/resolve/stub-resolv.conf* ]]; then
            pass "/etc/resolv.conf uses resolved stub"
        else
            warn "/etc/resolv.conf is a symlink, but not to resolved stub"
        fi
    else
        fail "/etc/resolv.conf is not a symlink"
    fi

    if ip route | grep -q '^default '; then
        pass "default route exists"
        ip route | grep '^default '
    else
        fail "no default route"
    fi

    if getent hosts archlinux.org >/dev/null 2>&1; then
        pass "DNS resolution works"
    else
        fail "DNS lookup failed"
    fi

    if ping -c 1 -W 3 archlinux.org >/dev/null 2>&1; then
        pass "internet connectivity works"
    else
        warn "ping failed; DNS may still work and ICMP can be filtered"
    fi

    echo
    networkctl --no-pager 2>/dev/null || true
    echo
    resolvectl status 2>/dev/null || true

    echo
    printf 'RESULT: %d failure(s), %d warning(s)\n' "$failures" "$warnings"
    (( failures == 0 ))
    EOF

    chmod +x ~/src/launch/health/10-network.sh

        pass "GitHub SSH authentication works"

10.3 HOW TMUX KEYBINDINGS WORK
-------------------------------------------------------------------------------

tmux has a PREFIX key.

Default:

    Ctrl-b

Most tmux commands are:

    press Ctrl-b
    release
    press another key

Example:

    Ctrl-b c

means:

    Ctrl-b
    then c

It does NOT mean hold Ctrl-b and c simultaneously.

DEFAULT USEFUL BINDINGS:

    Ctrl-b c
        new window

    Ctrl-b n
        next window

    Ctrl-b p
        previous window

    Ctrl-b %
        split left/right

    Ctrl-b "
        split top/bottom

    Ctrl-b arrow
        select pane

    Ctrl-b x
        kill pane

    Ctrl-b &
        kill window

    Ctrl-b d
        detach

    Ctrl-b [
        copy/scroll mode

    Ctrl-b ?
        list bindings

== 14. MAKE: WHAT IT ACTUALLY DOES ==
===============================================================================

You said you do not yet know Make well.

You will use Make to build dwl, so understand it BEFORE dwl.

-------------------------------------------------------------------------------
14.1 MAKE IS NOT A COMPILER
-------------------------------------------------------------------------------

This distinction is important.

    gcc / cc
        compiler + linker driver

    make
        decides WHICH commands need to run and WHEN

    Makefile
        file containing build rules

Example build manually:

    cc main.c -o hello

Make can automate that.

-------------------------------------------------------------------------------
14.2 SIMPLE MAKEFILE
-------------------------------------------------------------------------------

Create practice directory:

    mkdir -p ~/src/make-practice
    cd ~/src/make-practice

Create C file:

    cat > main.c <<'EOF'
    #include <stdio.h>

    int main(void)
    {
        puts("hello from make");
        return 0;
    }
    EOF

Create Makefile:

    cat > Makefile <<'EOF'
    CC = cc
    CFLAGS = -Wall -Wextra

    hello: main.c
    	$(CC) $(CFLAGS) main.c -o hello

    clean:
    	rm -f hello
    EOF

IMPORTANT:

The indented command lines inside a traditional Makefile MUST start with a TAB,
not spaces.

Run:

    make

Make reads:

    hello: main.c

as:

    TARGET: DEPENDENCIES

Meaning:

    build `hello`
    if:
        hello does not exist
        OR main.c is newer than hello

Then it runs:

    cc -Wall -Wextra main.c -o hello

Run:

    ./hello

Run make again:

    make

You will probably see:

    make: 'hello' is up to date.

WHY?

Because Make checked timestamps and decided rebuilding was unnecessary.

Change source:

    printf '\n' >> main.c

Now:

    make

It rebuilds because main.c is newer.

-------------------------------------------------------------------------------
14.3 MAKE VARIABLES
-------------------------------------------------------------------------------

In:

    CC = cc
    CFLAGS = -Wall -Wextra

Use with:

    $(CC)
    $(CFLAGS)

Common build variables:

    CC
        C compiler

    CFLAGS
        compiler flags

    CPPFLAGS
        preprocessor flags

    LDFLAGS
        linker flags

    LDLIBS
        libraries to link

    PREFIX
        desired installation prefix

Common prefix:

    /usr/local

This typically means:

    /usr/local/bin
    /usr/local/lib
    /usr/local/share

-------------------------------------------------------------------------------
14.4 TARGETS
-------------------------------------------------------------------------------

When you run:

    make

Make builds the default/first target.

When you run:

    make clean

Make explicitly asks for target:

    clean

When you run:

    make install

Make explicitly asks for:

    install

These target names are conventions, not magic language keywords.

-------------------------------------------------------------------------------
14.5 PHONY TARGETS
-------------------------------------------------------------------------------

If a target does not represent a real output file, Makefiles often declare:

    .PHONY: clean install

Why?

Otherwise, if a real file called `clean` existed, Make could decide:

    "clean already exists"

and skip the command.

-------------------------------------------------------------------------------
14.6 OBJECT FILES
-------------------------------------------------------------------------------

Large C builds usually do:

    source.c
        -> source.o
        -> final executable

Compile only:

    cc -c source.c -o source.o

Link:

    cc source.o other.o -o app

Why?

If only one source file changes, you rebuild one .o rather than every source
file.

dwl uses this style.

-------------------------------------------------------------------------------
14.7 CLEAN
-------------------------------------------------------------------------------

Typical:

    make clean

does NOT uninstall anything.

It usually removes generated build files:

    *.o
    generated headers
    executable

That lets you force a complete rebuild:

    make clean
    make

For dwl config changes, this is a useful simple habit.

-------------------------------------------------------------------------------
14.8 INSTALL IS JUST ANOTHER TARGET
-------------------------------------------------------------------------------

`make install` usually copies built files into system paths.

It is NOT the same thing as pacman.

Pacman tracks:
    package files
    versions
    dependencies
    ownership

A random `make install` normally does not.

For this guide we will:

    use `make` to BUILD dwl

but:

    manually install only the dwl binary

with:

    install -Dm755 dwl /usr/local/bin/dwl

WHY?

dwl's normal install target also installs:
    a man page
    a session desktop file

You do not use:
    a display manager
    local man documentation

So we deliberately install only the needed executable.

Removal is then completely obvious:

    rm /usr/local/bin/dwl

-------------------------------------------------------------------------------
14.9 INSPECT A MAKEFILE
-------------------------------------------------------------------------------

Before running make in unfamiliar source:

    sed -n '1,220p' Makefile
    sed -n '1,220p' config.mk

Look for:

    all:
    clean:
    install:
    CC
    CFLAGS
    PREFIX
    DESTDIR

Useful dry-ish inspection:

    make -n

`-n` prints the commands Make WOULD execute without actually executing most of
them.

For dwl:

    make -n

is a useful way to see how source files will be compiled.

== 16. NVIDIA DRIVER DECISION FOR YOUR RTX 3060 ==
===============================================================================

YOUR GPU:

    RTX 3060
    Ampere generation

CURRENT DRIVER:

    nouveau

TARGET DRIVER:

    nvidia-open

WHY nvidia-open?

As of this guide's snapshot:

    NVIDIA upstream recommends the open kernel module on supported GPUs.

Ampere is supported.

Arch's current package set recommends:

    stock `linux` kernel:
        nvidia-open

    stock `linux-lts`:
        nvidia-open-lts

    arbitrary/custom kernels:
        nvidia-open-dkms

You are using the normal Arch `linux` package.

Therefore the simplest current choice is:

    nvidia-open

NOT:

    nvidia-open-dkms

Why avoid DKMS here?

DKMS is useful when:
    you use custom kernels
    you use multiple kernels
    you need modules rebuilt locally for arbitrary kernels

You currently do not.

The prebuilt kernel-matched package is simpler.

-------------------------------------------------------------------------------
16.1 IMPORTANT: OPEN KERNEL DRIVER DOES NOT MEAN FULLY OPEN USERSPACE
-------------------------------------------------------------------------------

nvidia-open contains the open-source kernel-module flavor.

It depends on:

    nvidia-utils

The NVIDIA userspace OpenGL/Vulkan/driver libraries are still NVIDIA's
userspace driver stack.

This package is large.

That is NOT accidental desktop bloat.

For NVIDIA hardware, these are the driver components needed for high-performance
graphics.

-------------------------------------------------------------------------------
16.2 FUTURE PACSTRAP: CHOOSING THE RIGHT DRIVER FROM THE START
-------------------------------------------------------------------------------

THIS SECTION IS FOR A FUTURE REINSTALL.

For THIS RTX 3060 + stock Arch `linux`, your pacstrap can include:

    base
    linux
    mkinitcpio
    e2fsprogs
    dosfstools
    amd-ucode
    linux-firmware-realtek
    nvidia-open

You would NOT need to intentionally select Nouveau.

Example:

    pacstrap -K /mnt \
        base \
        linux \
        mkinitcpio \
        e2fsprogs \
        dosfstools \
        amd-ucode \
        linux-firmware-realtek \
        nvidia-open

`nvidia-open` pulls the matching userspace driver dependency.

You generally do not need `linux-firmware-nvidia` for the NVIDIA packaged
driver stack, because nvidia-utils ships the firmware used by that driver.

`linux-firmware-nvidia` is the generic Linux firmware bundle for NVIDIA
hardware, particularly relevant to in-kernel drivers such as Nouveau/Nova.

== 23. AUDIO: MINIMAL DAILY-DRIVER STACK ==
===============================================================================

Linux audio layers:

    hardware
        |
        v
    kernel audio drivers
        |
        v
    ALSA
        |
        v
    PipeWire
        |
        v
    WirePlumber
        |
        v
    applications

ALSA is the low-level kernel/userspace audio interface.

PipeWire is the modern media graph/server.

WirePlumber is the policy/session manager deciding how devices and streams are
connected.

For broad desktop application compatibility, install:

    pipewire
    pipewire-audio
    pipewire-pulse
    pipewire-alsa
    wireplumber

WHY pipewire-pulse?

Many desktop applications speak the PulseAudio protocol.

pipewire-pulse provides that protocol without running PulseAudio itself.

WHY pipewire-alsa?

Tiny package that routes ALSA-configured applications through PipeWire when
appropriate.

This costs almost nothing and avoids inconsistent "some apps bypass PipeWire"
behavior.

Create:

    cat > ~/src/launch/install/90-audio.sh <<'EOF'
    #!/usr/bin/env bash
    set -euo pipefail
    (( EUID == 0 )) || { echo "run as root"; exit 1; }

    packages=(
        pipewire
        pipewire-audio
        pipewire-pulse
        pipewire-alsa
        wireplumber
    )

    pacman -Sp --needed --print-format '%n  %v  %s  %d' "${packages[@]}"
    pacman -Syu --needed "${packages[@]}"
    EOF

After normal user login, systemd user activation normally starts these.

Inspect:

    systemctl --user status pipewire.service
    systemctl --user status pipewire-pulse.service
    systemctl --user status wireplumber.service

Control:

    wpctl status

Volume:

    wpctl set-volume @DEFAULT_AUDIO_SINK@ 5%+
    wpctl set-volume @DEFAULT_AUDIO_SINK@ 5%-

Mute:

    wpctl set-mute @DEFAULT_AUDIO_SINK@ toggle

== 30. START DWL SESSION SERVICES CLEANLY ==
===============================================================================

So far you manually launched:

    fnott &

Now create a session script.

IMPORTANT DWL DETAIL:

The program passed to:

    dwl -s '...'

receives dwl status information on stdin.

If your script does not consume it, close stdin.

Otherwise dwl can eventually block writing status output.

Create:

    cat > ~/src/launch/bin/dwl-session <<'EOF'
    #!/usr/bin/env bash
    set -euo pipefail

    # dwl writes status information to this child's stdin.
    # We do not use status information, so close it immediately.
    exec <&-

    # Export Wayland-session values to services launched by the user systemd
    # manager / D-Bus activation.
    dbus-update-activation-environment --systemd \
        WAYLAND_DISPLAY \
        XDG_CURRENT_DESKTOP \
        XDG_SESSION_DESKTOP \
        XDG_SESSION_TYPE

    systemctl --user import-environment \
        WAYLAND_DISPLAY \
        XDG_CURRENT_DESKTOP \
        XDG_SESSION_DESKTOP \
        XDG_SESSION_TYPE

    # Notification daemon.
    fnott &

    wait
    EOF

Why `wait`?

dwl treats the `-s` program as its session child.

We want this script to remain alive while its background children live.

Update start script:

    cat > ~/src/launch/bin/start-dwl <<'EOF'
    #!/usr/bin/env bash
    set -euo pipefail

    export XDG_CURRENT_DESKTOP=dwl
    export XDG_SESSION_DESKTOP=dwl
    export XDG_SESSION_TYPE=wayland

    exec dwl -s "$HOME/src/launch/bin/dwl-session"
    EOF

Make executable:

    chmod +x ~/src/launch/bin/{start-dwl,dwl-session}

WHY PORTALS IF YOU HAVE NO DESKTOP ENVIRONMENT?

Applications still need standard desktop integration for things such as:

    screen sharing
    screenshots
    file selection

A portal is a D-Bus API.

Front-end:

    xdg-desktop-portal

asks specialized backend implementations to perform the operation.

For wlroots screen sharing:

    xdg-desktop-portal-wlr

For your terminal file chooser:

    xdg-desktop-portal-termfilechooser fork

The route becomes:

    application
        |
        v
    xdg-desktop-portal
        |
        +-- ScreenCast/Screenshot
        |      -> xdg-desktop-portal-wlr
        |
        `-- FileChooser
               -> terminal FileChooser backend
                    -> foot
                         -> fd
                         -> fzf

    fail() { printf '[FAIL] %s\n' "$*"; failures=$((failures + 1)); }

    echo '=== PORTAL HEALTH ==='

    for pkg in xdg-desktop-portal xdg-desktop-portal-wlr; do
        if pacman -Q "$pkg" >/dev/null 2>&1; then
            pass "$pkg installed"
        else
            fail "$pkg missing"
        fi
    done

    if pacman -Q xdg-desktop-portal-termfilechooser-hunkyburrito-git \
        >/dev/null 2>&1
    then
        pass "terminal FileChooser backend installed"
    else
        fail "terminal FileChooser backend missing"
    fi

    if systemctl --user is-active --quiet xdg-desktop-portal.service; then
        pass "xdg-desktop-portal active"
    else
        fail "xdg-desktop-portal inactive"
    fi

    if systemctl --user is-active --quiet xdg-desktop-portal-wlr.service; then
        pass "xdg-desktop-portal-wlr active"
    else
        warn "wlr backend not currently active; it may D-Bus activate on demand"
    fi

    env_dump="$(systemctl --user show-environment 2>/dev/null || true)"

    if grep -q '^WAYLAND_DISPLAY=' <<<"$env_dump"; then
        pass "WAYLAND_DISPLAY imported into user systemd"
    else
        fail "WAYLAND_DISPLAY missing from user systemd environment"
    fi

    if grep -q '^XDG_CURRENT_DESKTOP=dwl$' <<<"$env_dump"; then
        pass "XDG_CURRENT_DESKTOP=dwl imported"
    else
        fail "XDG_CURRENT_DESKTOP=dwl missing from user systemd environment"
    fi

    conf="$HOME/.config/xdg-desktop-portal/portals.conf"

    if [[ -f "$conf" ]]; then
        pass "portal routing config exists"
        cat "$conf"
    else
        fail "portal routing config missing"
    fi

    echo
    echo "--- portal logs ---"
    journalctl --user \
        -u xdg-desktop-portal.service \
        -u xdg-desktop-portal-wlr.service \
        -n 30 \
        --no-pager 2>/dev/null || true

    echo
    printf 'RESULT: %d failure(s), %d warning(s)\n' "$failures" "$warnings"
    (( failures == 0 ))
    EOF

This is CHECKPOINT 8.

A full FileChooser end-to-end test ultimately requires an application that
actually requests the XDG FileChooser portal.

When you later install a browser, configure that browser to use the portal if
it does not do so by default.

37.1 UNDERSTAND A KEY ENTRY
-------------------------------------------------------------------------------

Typical shape:

    {
        MODIFIER,
        XKB_KEY_KEY,
        function,
        argument
    }

Example conceptually:

    {
        MODKEY|WLR_MODIFIER_SHIFT,
        XKB_KEY_Return,
        spawn,
        {.v = termcmd}
    }

Read it as:

    When:
        MODKEY + Shift + Return

    call:
        spawn()

    with:
        termcmd

The syntax:

    MODKEY | WLR_MODIFIER_SHIFT

uses C bitwise OR to combine modifier flags.

-------------------------------------------------------------------------------

    openssl enc \
        -aes-256-cbc \
        -pbkdf2 \
        -salt \
        -a \
        -in ~/nvidia-health.txt \

It will prompt for the encryption password.

    openssl enc \
        -d \
        -aes-256-cbc \
        -pbkdf2 \
        -a \
        -in ~/nvidia-health.txt.enc \
        -out ~/nvidia-health.txt

Avoid:

    -pass pass:SECRET

in interactive shell history unless you deliberately accept that exposure.
